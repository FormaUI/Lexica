# Implementation decisions

The decisions taken while implementing the plan from step 5 of unit 1 through unit 5 without a review of each, so the work goes on uninterrupted: each is recorded here as it is taken, with its reason and what it departs from, if anything, and all of them are reviewed together before unit 6, when any is changed. A decision that settles what the specification leaves open is recorded in the specification too, where its subject lives, and links back here until its review.

**State:** awaiting review. An entry is reviewed once it is marked ✅ reviewed, or changed as its review decides.

| ID | Where | Decision | Reason | Departs from |
| --- | --- | --- | --- | --- |
| I1 | S1, nested declarations | A module error's location names the type a nested declaration stands in as `type`, beside `module`, `declaration` and `declarationKey`: `{ module, type, declaration, declarationKey }` | The specification requires the location to name that type, [creating a module](../../spec/modules.md#modules-declarations), and names none of the location's attributes; `lexica.d.ts` declares them, and `type` follows `module` and `declaration`, each named for what it locates | Nothing |
| I2 | S1, nested declarations | The nested declarations land in two commits: a reference type's own members within it first, with the registry's nested traversal, a member's containing type as its receiver, a type's `import` covering its members and the location of I1; then `kind: 'structured'`, its data shape the properties it declares directly without `updates`, in place of `fields` | The traversal and its context are the machinery both need, and a reference type's members exercise them without changing how data is read, so the second commit changes the data shape alone | Nothing; the status overview left the boundary to be settled here |
| I3 | S1, nested declarations | A collision of a member declared within a type, LEXICA4029 or LEXICA4551, is located at its `name`, where a flat member's is at its `target` | A nested member names no target, and its name is what collides within the type | Nothing |
| I4 | S1, nested declarations | A type's `members` that are not a list are refused with LEXICA4503, at the type and the declaration key `members` | LEXICA4503 is "a module's declarations of one kind that are not a list", and a type's members are declarations of one kind; no other code covers them | Nothing |
| I5 | S1, structured types | A property of a structured type's data shape resolves as `{ kind: 'dataProperty', declaration, name }`, read from the data by the evaluator's stored-value read, never invoked: it is a used declaration, as every declaration a resolution selects is, and reaches no `beforeInvoke`, which is called before an implementation is invoked | The specification reads a data property from the data, never invoking an implementation, and counts every selected declaration among the used declarations; the kind follows the registry's `getDataPropertyTypes`, so `'storedValue'` reads object fields alone and becomes `'objectField'`, as the ledger's decision 3 planned | Nothing |
| I6 | S1, structured types | A structured type may declare no data property: LEXICA4509 retires, and its data shape is empty | The specification's catalog has no condition for it, and a structured type of members alone is well-formed | The current implementation, which refuses it |
| I7 | S1, the `indexer` kind | A used unnamed indexer, which declares no name, has the `name` null and the `qualifiedName` of its receiver type followed by brackets, `List[]`, as its access is written after its receiver; where its receiver type is any receiver or a type parameter, `[]` | The specification names neither; `qualifiedName` qualifies a member by its receiver type as `List.count` does, and brackets after the type say what the access writes | Nothing; a used declaration's `name` was always a string |
| I8 | S1, the `indexer` kind | `lexica.declarations.indexer(name, target, result, options)` declares an indexer, its name null for an unnamed one; the helpers' `syntax` and `isDefault` options go, since the keys they wrote are refused | The helpers write declaration keys, and S1 removes `syntax` and `default`, so an indexer needs a helper now; M1 renames every helper at S2, this one to `createIndexerDeclaration`, so each helper's signature changes once more, with its receiver | The status overview's S2 placing of `createIndexerDeclaration`, which this helper becomes there |
| I9 | S1, the `indexer` kind | A location names an unnamed indexer, which declares no name, `[]`, as its access is written; a collision of two unnamed indexers, LEXICA4068 or LEXICA4550, is located at the declaration key `kind` | A location names its declaration, and an unnamed indexer has no name of its own; its kind, an indexer, with no name, is what makes it the type's unnamed one | Nothing |
