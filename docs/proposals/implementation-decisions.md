# Implementation decisions

The decisions taken while implementing the plan from step 5 of unit 1 through unit 5 without a review of each, so the work goes on uninterrupted: each is recorded here as it is taken, with its reason and what it departs from, if anything, and all of them are reviewed together before unit 6, when any is changed. A decision that settles what the specification leaves open is recorded in the specification too, where its subject lives, and links back here until its review.

**State:** awaiting review. An entry is reviewed once it is marked ✅ reviewed, or changed as its review decides.

| ID | Where | Decision | Reason | Departs from |
| --- | --- | --- | --- | --- |
| I1 | S1, nested declarations | A module error's location names the type a nested declaration stands in as `type`, beside `module`, `declaration` and `declarationKey`: `{ module, type, declaration, declarationKey }` | The specification requires the location to name that type, [creating a module](../../spec/modules.md#modules-declarations), and names none of the location's attributes; `lexica.d.ts` declares them, and `type` follows `module` and `declaration`, each named for what it locates | Nothing |
| I2 | S1, nested declarations | The nested declarations land in two commits: a reference type's own members within it first, with the registry's nested traversal, a member's containing type as its receiver, a type's `import` covering its members and the location of I1; then `kind: 'structured'`, its data shape the properties it declares directly without `updates`, in place of `fields` | The traversal and its context are the machinery both need, and a reference type's members exercise them without changing how data is read, so the second commit changes the data shape alone | Nothing; the status overview left the boundary to be settled here |
| I3 | S1, nested declarations | A collision of a member declared within a type, LEXICA4029 or LEXICA4551, is located at its `name`, where a flat member's is at its `target` | A nested member names no target, and its name is what collides within the type | Nothing |
| I4 | S1, nested declarations | A type's `members` that are not a list are refused with LEXICA4503, at the type and the declaration key `members` | LEXICA4503 is "a module's declarations of one kind that are not a list", and a type's members are declarations of one kind; no other code covers them | Nothing |
| I5 | S1, structured types | A property of a structured type's data shape resolves as `{ kind: 'dataProperty', declaration, name }`, read from the data by the evaluator's stored-value read, never invoked: it is a used declaration, as every declaration a resolution selects is, and reaches no `beforeInvoke`, which is called before an implementation is invoked | The specification reads a data property from the data, never invoking an implementation, and counts every selected declaration among the used declarations; the kind follows the registry's `getDataPropertyTypes`, so `'storedValue'` reads object fields alone and becomes `'objectField'`, as the ledger's decision 3 planned | Nothing |
| I6 | S1, structured types | A structured type may declare no data property: LEXICA4509 retires, and its data shape is empty | The specification's catalog has no condition for it, and a structured type of members alone is well-formed | The current implementation, which refuses it |
| I7 | S1, the `indexer` kind | A used unnamed indexer, which declares no name, has the `name` null and the `qualifiedName` of its receiver type followed by brackets, `List[]`, as its access is written after its receiver; where its receiver type is any receiver or a type parameter, `[]` | The specification names neither; `qualifiedName` qualifies a member by its receiver type as `List.count` does, and brackets after the type say what the access writes | Nothing; a used declaration's `name` was always a string |
| I8 | S1, the `indexer` kind | `lexica.declarations.indexer(name, target, result, options)` declares an indexer, its name null for an unnamed one; the helpers' `syntax` and `isDefault` options go, since the keys they wrote are refused | The helpers write declaration keys, and S1 removes `syntax` and `default`, so an indexer needs a helper now; M1 renames every helper at S2, this one to `createIndexerDeclaration`, so each helper's signature changes once more, with its receiver | The status overview's S2 placing of `createIndexerDeclaration`, which this helper becomes there |
| I9 | S1, the `indexer` kind | A location names an unnamed indexer, which declares no name, `[]`, as its access is written; a collision of two unnamed indexers, LEXICA4068 or LEXICA4550, is located at the declaration key `kind` | A location names its declaration, and an unnamed indexer has no name of its own; its kind, an indexer, with no name, is what makes it the type's unnamed one | Nothing |
| I10 | S1, mappings | A mapping's key that is no string is refused with LEXICA4008, located at the declaration key `key`, and a mapping is located by its key | A key is any string, as a fixed argument gives it, so one that is no string is a mapping without its key, LEXICA4008's condition; the key tells a selector's mappings apart, as a name tells other declarations apart | The retired LEXICA4511, which refused a key by its spelling |
| I11 | S1, `internal` | A flat member's `target` counts among the types it writes: a public flat member targeting an internal type of its module is refused with LEXICA4052, and one targeting another module's internal type with LEXICA4018 | The specification refuses an extension's target naming another module's internal type, and bounds a member's accessibility by the type that holds it; until S2 gives a flat member an extension, its target is where its receiver is written, so it counts as the extension's target will | Nothing; S2 replaces the flat member's target with its extension's |
| I12 | S1, the scalar type names | `Type's` `PRIMITIVE_TYPE_NAMES`, the scalar names by `typeof`, stays `Type's` own, and a test asserts it names exactly `LexicaModule.scalarTypeNames` | `Type` is the leaf every stage builds on and imports nothing, and `LexicaModule` imports it; deriving the map from `LexicaModule` would make the leaf depend on the vocabulary, a cycle the test avoids while keeping the two lists one | The ledger's U7, which derives `PRIMITIVE_TYPE_NAMES` from the scalar list |
| I13 | S2 | S2 lands in four commits: extension types, with names that declare type parameters and scopes for them; the registration checks of type parameters; Lexica's own module, `List<T>` through its internal form and `VerbExtensions<T>`, with U6 and U7's built-in names; and the flat form removed, with M1's helpers, M6 and M15, every test migrated | Each commit builds on the one before and passes the gate alone; the flat form goes last, since every test module declares through it, and its migration then changes each test once | Nothing |
| I14 | S2, extension types | Until the flat form goes, a member declared flat with its `target` keeps reading every single capital letter as a type parameter, and every other declaration reads the parameters its name and its extension's declare, any other name a type's: a type, an extension, a member within either, a module member, a mapping and a conversion | The specification's declared parameters replace the implicit ones, and the flat form is the one that has no place to declare them, its receiver written in a target; S2's last commit removes it, and the implicit reading with it | The specification, for the flat form alone, until it goes |
| I15 | S2, Lexica's own module | `Vocabulary` holds Lexica's value types through its internal form: `Number`, `String` and `Boolean` of kind `scalar`, and `List` of kind `generic`, its `typeParameters` names as every declaration's are, `['T']`, and its `variances` in their order, `['covariant']`, with the members of lists within it. Those members are validated, copied and frozen by a module created for that alone and never registered, an extension of `List<T>`; the registry registers them with Lexica's own module where it registers `Vocabulary.module`, by identity, and `VerbExtensions<T>` is an ordinary extension of that module. `getTypeDeclaration` replaces `getStructure`, `getReferenceType` and `getGenericType`, `isReferenceType` kept as the predicate it reads; `Vocabulary.builtInTypeNames` replaces `LexicaModule.builtInTypeNames`, derived from the value types | The specification gives Lexica's own module `List<T>` and no module form for a generic type, so the form stays Lexica's; a separate key of variances keeps `typeParameters` one shape, names, wherever it stands; module creation's own validation keeps one contract for every member; and the built-in names move to `Vocabulary`, which owns the types they name, since `LexicaModule` imports nothing of it | Nothing |
| I16 | S2, the duplicate checks | The duplicate tolerance check is module creation's LEXICA4026, which refused a tolerance on a scalar result of no number or a list before the registry's own check, which knows every type and refuses each of them, so registration alone checks it, creation keeping LEXICA4515's check of the number; the duplicate identifier check is `LexicaModule.#isIdentifier`, `Names.isIdentifier`'s pattern written again for an observation type's identity, which now reads `Names.isIdentifier`. Both go in a commit of their own, before the flat form's removal | The plan names the two checks without saying which copy goes; a rule kept once belongs where its whole contract can be checked, and a name's pattern has one owner. A tolerance on a `String` result is now refused when the module is registered, not when it is created | Nothing |
