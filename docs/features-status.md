The implementation reads definition version 35, its node names, its imports and its collection expressions, the language's indexers, computed properties and qualified type names, its types' names in PascalCase, and each type identified by its module. Its declarations take the specification's shape: reference types, with their hierarchy, membership and recognition, and structured types, each holding its members; extensions; operators; declared type parameters; and `Any`. One selector chooses every member, indexer and operator, at resolution and, for a value of `Any`, as it is evaluated. A script imports the modules and the types whose vocabulary it uses, a host supplying imports beside its own, and resolution reaches only what they make available, Lexica's own always among it. An extension access, `device:Energy.Device.usage`, selects among one extension's members, its function read without a call a reference bound to its receiver. Scripts follow line structure, and their canonical text reads back as the same definition. Collections are lists, dictionaries and pairs, a script writing them as collection expressions; their construction from members, their operations, positions and ordering follow in unit 4.

The bundle and type declarations are built. npm and NuGet packages are packed locally but unpublished. Every example the specification and the README give resolves against [the examples' vocabulary](../spec/examples-vocabulary.md) and evaluates in the gate: 40 blocks, 75 examples with each line of a block of single forms its own, a host call prepared and projected, and the one the specification documents as refused refused.

The [specification](../spec/README.md) defines the contract; the [design](lexica-design.md) explains the architecture. This file tracks implementation and the remaining work. "Implemented" means built and tested in the gate for the current implementation version; it does not imply that later specification changes are implemented.

## Implementation plan

The remaining work is grouped by the code it rewrites, so each mechanism is rewritten once: the declaration model and the registry, the type relation, the member selector, argument binding, the text pipeline, and the evaluator's member selection. The units are ordered by what each needs from the one before it.

- **A stage is a commit.** Each stage passes the gate, and moves each aspect once: a declaration, a test or a document takes its final form the first time the aspect changes, never an intermediate one a later stage replaces.
- **Breaking changes are made directly,** without compatibility layers, migration notes or deprecations, until the beta. The one exception is the working checklist each host migration checkpoint keeps, of the changes its host has still to adopt, which is removed once that migration is verified.
- **Three host migration checkpoints.** A host building on Lexica builds against a pinned commit, and migrates its declarations and its runtime use once at the end of unit 2, its scripts once at the end of unit 3, and its handling of collections in results once at the end of unit 4. The release then changes how it consumes Lexica, through the published packages.
- **Documents move with their stage.** The README, the [embedding guide](embedding-guide.md), the type declarations and this file change in the stage that changes what they describe.
- **Every diagnostic has its code.** Unit 0's third stage gives a [code](proposals/diagnostic-codes.md) to every existing condition, and every later stage gives each condition it introduces its code at once; the tests of each condition assert its code, never only its message.

### Type identity and names

**Implemented.**

- Type names in PascalCase, Lexica's own among them, `Number` and `List<T>`, and a module's type checked for its initial capital when the module is created. Lexica's own names are reserved.
- A type identified by its module and local name, so different modules declare the same local name; a structured type's `import` and qualified type references, every reference resolved to its identity at registration; and an argument's diagnostic writing the type it expects and the one it finds by their qualified names where they share a local name. A type name qualified by a module names it through the local name the script's imports give that module, and an unqualified one by the script's tiers: a type import's local name, then Lexica's own, then the one public type of its name among the modules the script imports. A declaration's, a declared binding's and a script's names are each read in a scope of their own, `TypeNameScope`, through the registry's one path, `resolveTypeName`.

### Indexers and computed properties

**Implemented.** A named indexer is written `x.name[k]`, a type's unnamed indexer `x[k]`, and a property by a computed name `x.[p]`, each optional as `x?.name[k]`, `x?[k]` and `x?.[p]`. Resolution reads `x.name[k]` as the named indexer wherever the receiver's type declares one, a key it refuses being its own error, and reads the property and indexes its answer only where none is declared. A colon in a chain begins an extension access, `x:Ext[k]` an extension's unnamed indexer and `x:Ext.name[k]` its named one, and a colon brackets follow directly is refused with the forms to write.

### Definition versions 34 and 35

**Implemented.** Version 35 adds the collection expressions a script writes, a `list` of its `items` and a `dictionary` of its `entries`, each its key's string and its value. A definition records its imports, each once in order of the local name it gives, and its nodes by version 34's names: `scriptParameter`, `memberAccess` and `indexerAccess` holding their `receiver`, a `call` holding its `callee`, the member access or the local it calls, an `object` its `objectFields` and its `context`, `arithmeticNegation`, an `operand` on a cast, a conversion and an attempt, and an optional chain's `chain`. Casts and conversions name a type qualified by its module's local name, as `to Home.Climate`, and an indexer is recorded without a `name`, a named indexer's receiver being the `memberAccess` node of its name. A definition's `extension` selections are validated, its module's local name checked against the imports, and resolved through the extension they name; the language version, `1.0.0-alpha.34`, follows at its step 8.

### Host calls

**Implemented.** Lexica prepares calls and projects host-supplied values; the host owns their lifecycle.

- `invokedBy: 'host'` declarations accept value parameters only, with no updates or implementation.
- Calls are allowed only in terminal position, including a body returning the call after locals or a terminal `do` block. Other positions are refused at resolution with a validation error.
- A fixed argument can select the result type through a type selector. Modules may add keys to an existing type selector, but registration rejects a key already declared in that selector.
- `resolution.hostCall` describes the call, with a null result type when the host supplies no result.
- `prepareHostCall` evaluates preceding locals once and retains their frame in the prepared call. It reports a skipped call when there is nothing to invoke.
- Each prepared call's `project` captures a supplied value as the declared result and evaluates its projection independently of other preparations from the same evaluator. Calls that supply no result have no projection.

Contracts: [Host-call declarations](../spec/members.md#members-host-calls), [host calls in the host contract](../spec/runtime.md#runtime-host-calls).

## Open decisions

The decisions taken while implementing step 5 of unit 1 through unit 5, each without its own review, are recorded in [implementation decisions](proposals/implementation-decisions.md), and reviewed together before unit 6. A first review keeps the design and found lineage that followed equal values rather than occurrences, and lineage lost, which unit 6 waits for: [D26](proposals/responsibilities-and-terminology-ledger.md#3-defects) realigns it by position, D27 keeps it in a filtered selection's metadata, and D28 carries it through a slice and `pick`; D29, found beside them, keeps an ordering of a list of collections through its capture.

Two open decisions are recorded. The first: a module that declares a type spelled as one of Lexica's own, as `Home.Number`, can't name Lexica's own type of that name in its own declarations, since [type name lookup](../spec/types.md#types-type-name-lookup) finds the module's own first and Lexica's own types have no qualified spelling. Giving Lexica a permanent namespace for that was declined; the limitation stands until another spelling is chosen.

The second: a type parameter's default is checked at registration to be data, and against what the parameter binds to nowhere, since resolution checks the arguments a call gives and passes a default left out as it is, so `0` reaches an implementation whose `T` is `String`. Whether resolution refuses such a call, or a parameter of a type parameter takes no default, is open.

Unit 0's decisions are taken, and unit 4 settles the collections proposal's open contracts, the lineage representation first. Deferred items below require their stated trigger before design or implementation resumes.
