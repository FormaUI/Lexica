# Lexica Design v1.0.0-alpha

The [Lexica specification](lexica-specification.md) defines the language. This design sets out how its modules are declared and registered, how it evaluates an expression for the host that asks, and how tooling reads its text; the [DOMQL design](https://github.com/FormaUI/DOMQL/blob/main/docs/domql-design.md) sets out how DOMQL, a host, observes, watches and carries out the queries written in it.

## Modules

An extension is registered as a module, which declares under its name the state members, event sources, actions and behaviors it contributes and supplies the implementation that carries each out; requests resolve against those declarations. The declarations are data, each member's name in the language, signature, result type, argument types and kinds and the request kinds it supports, so they can be read without running the implementations. A module associates two things explicitly, and neither is derived from the other: an operation's name in the language, `style`, and the function that carries it out, whatever that function is called. A module registers under a name of its own, and registering a name twice is an error.

```js
const virtualizer = lexica.createModule('virtualizer', declarations, functions);
const registry = lexica.createRegistry([virtualizer]);
```

### Declarations

A module is created with its members and, once it can carry them out, the functions they name; declarations are validated when the module is created and checked against the registry when it is registered. Lexica's own vocabulary is a module Lexica creates itself, the one module every registry holds; every other module, a host's as DOMQL's `domql` is, is made with `createModule`, and no factory, name or flag makes one an exception to the rules. A module declares members and conditions of any name on any type, its own or another module's, and a member or condition already declared for an overlapping receiver is refused at registration; it declares conversions to or from its own types alone, a rule Lexica's own module alone is exempt from, for the conversions between the language's types.

- **A declaration** names the member's name in the language, and the key of its function in the module's functions, independent of its name; its kind, one of property, operation, source, action and behavior; for a member that is no property, its form, a call by default or, for an operation, a named indexer, whose one required value parameter is its key, which can be the default indexer of its receivers, one for any receiver, and, where it has parameters, its input, positional, its parameters in order, or options, one object whose fields supply its parameters however many it has, as the specification sets out; the types it applies to; its parameters; its result type; its observation coverage; and, for a member that answers a number or a structured value holding numbers, the `tolerance` within which a watch compares each of them, exactly where it declares none.
- **A parameter** is a value or an expression. An expression is evaluated against each item of the list it follows and declares the type it produces. A parameter declares whether it is required, its default where it is not, and whether a null argument propagates, making the call answer null, or is accepted.
- **A fixed parameter** names something the vocabulary resolves before any evaluation, and declares what it selects: an event type or a condition.
- **A condition** names a Boolean of the receivers it applies to, the key of the function that tests it and its own contract, how it changes, how it reads, its misses and its observations, as a member's is. A member whose fixed argument selects a condition, as `is` does, names no function and derives how it changes: the resolution keeps both, the member, which gives the request its form, its argument and its type, and the condition, whose function carries it out and whose contract a watch checks and the evaluation follows, so one condition's observability is no other's. A module names conditions freely on any type, as it does members, and a condition's failures name it, the member that selected it and its module.
- **Observations.** A member that changes observably or partly observably names the observations that cover its changes. An observation is of a type, observes the receiver, the receiver's root, its roots, the window, the document or an argument of the member, and gives the arguments its type takes, as `{ type: 'resize', of: 'receiver' }` does: a literal, a list of values, or an argument of the member, `{ argument }`, which can carry a prefix, a string joined before the argument of a value parameter of type `string`, as `{ argument: 'name', prefix: 'aria-' }` gives the attribute the ARIA view's indexer reads, so the observation names that attribute and is shared with every other observation of it; a member that changes in any other way names none. The receiver's **root** and its **roots** are those [trees and slots](https://github.com/FormaUI/DOMQL/blob/main/docs/domql-design.md#trees-and-slots) defines: a member that depends on the structure around its receiver observes its root, as `all` and `closest` do, and one that depends on any tree its receiver is shown in observes its roots, as `rect` does for scrolling. An observation of the roots is one request at each, so it is an invalidation, and a maintained observation, which gives its member one sample, observes one target. A module declares a type of observation by a camelCase name, its contract, the arguments that belong to an observation's identity, whether equivalent requests share one, and the function that starts one, which takes the request, the function it calls when something may have changed and the environment, and answers an object whose `stop` ends the observation and, for a maintained type, whose `sample` answers its latest sample as `{ pending, value }`, pending until the first arrives; a member reads the value, and is not called while a sample it reads is pending, answering null. An observation of a type that is not shared is kept for each watch, `evaluateAsync` call and event listener alone, so the sample it delivered reaches that caller's later evaluations. DOMQL's `domql` module declares the types `resize`, `mutation`, `attachment`, `intersection`, `media`, `pixelRatio`, `event` and `visibility`, each shared; `intersection` is maintained, and the others are invalidations. A `resize` observes an element's border box, its content box, or both as its `client` box, DOMQL's combined mode, which starts one native observer for each box under one observation and lets go of the first where the second fails to start. A type is either an invalidation observation, which says that a result may have changed and carries no value, or a maintained observation, which provides a sample a member reads and is pending until its first arrives; a member that reads maintained values names a maintained observation, and no other member does.
- **Functions.** A member takes its receiver, its arguments by name and the environment, and a member that reads maintained values also their values, in the order its declaration names the observations. A source takes its receiver, its arguments, the environment and the function it delivers each event to, and answers an object whose `stop` ends the listening. An action takes its receiver, its arguments, the environment and `{ signal }`, and answers its result or a promise of it. A behavior takes its receiver, its arguments, the environment and `{ reportError }`, starts before it returns, and answers an object whose `update(receiver, args)` applies new arguments and whose `dispose` ends it.
- **A conversion** names the type of data it converts from, the one it converts to and the key of its function, one for each source type and target across every module registered, and none from a type to itself, which a value already of it converts to by the language's rule. Its types are `number`, `string`, `boolean` and the structured types that hold data alone, lists of data among their fields: a node and an event source are left to members, which declare how they change, so a conversion adds no dependency on the document, and a list itself is no type a conversion converts between. A conversion takes the value, never null, and `{ reject }`, reads nothing else, and answers the converted value, which is checked against the type it converts to, or calls `reject(reason)` where the value has none, with a reason that is a diagnostic string. `reject` throws a signal private to Lexica and to that attempt at the conversion, so it never returns and the conversion stops where it calls it, unlike a promise's `reject`. A rejection is the one failure a conversion expects: `to` fails the evaluation for it and `try … to "type"` answers null, carrying the conversion out by one path, and any other exception, and a value not of the type, is a fault, which fails the evaluation for either. `to` takes one declared conversion and never chains them.
- **Types and events** are contributed by modules as data: structured types with their fields and event types with the type of their event data; a test is a member that answers a Boolean, and a capability a condition `supports` asks.
- **Observation coverage** states how a member changes (constant, observable, partly observable with the changes it misses, unobserved, or derived from the items it selects and the expression it evaluates) and how it reads (fresh, maintained, captured or derived).

`registry.resolve(source, bindings)` resolves a request: it resolves every member against the registry, types the result and records what each member resolved to, without a browser and without evaluating anything. What may be watched is the host's to decide from the change categories of the members a resolution uses: DOMQL refuses a watch over a member that is unobserved, and one over a partly observable member unless it accepts partial observation.

A module is given the capability it exposes, never an instance of it, since instances belong to the callers that apply them. A module exposes a capability through Lexica without the capability depending on Lexica: the capability keeps an API of its own, and its module lives beside it or in an integration package for it.

### Registries

A host resolves and evaluates against a registry of its own, which `lexica.createRegistry(modules)` creates holding Lexica's own module and the modules given; no registry is shared, so two hosts never see each other's modules.

- **The registry holds definitions.** A registry holds the declarations of every module registered with it, shared by all the host's callers. The instances behaviors create, the event listeners subscribed to them and the state of whoever applied them are scoped to their callers, never to the registry.
- **Registering checks the module whole.** `registerModule` checks every declaration against the registry before it registers any, so a module refused leaves nothing of itself registered; a module's name is registered once.
- **Its revision.** A registry answers a revision that changes whenever its vocabulary does, so a host that keeps resolutions knows when to resolve again.
- **Registering is not applying.** Registering a module makes its capability understood; applying one of its behaviors creates an instance for its caller and target. Disposing that instance leaves the module registered.
- **Registering comes first.** A module is registered before a request naming it is resolved, and a member no registered module declares is a validation error naming it.

## Evaluation

Lexica evaluates an expression it has resolved against a registry, once and synchronously, for the host that asks. The host gives it an environment and, where it observes what an evaluation reads, three hooks; Lexica carries the evaluation out, and the host keeps everything that spans evaluations.

```js
const result = registry.evaluate(source, bindings, {
    env: { window, document },
    beforeInvoke(request) { /* observe the read; answer a maintained member's samples */ },
    afterInvoke(request, value) { /* note the value read */ },
    afterEvaluation(outcome) { /* keep or close what the evaluation opened */ },
});
```

- **The evaluator.** Lexica evaluates each node of the resolution, invokes each member's implementation with its receiver, its arguments and the environment, checks the value it answers against the member's result type, and fails the evaluation at the member's location with an evaluation error where an implementation throws or answers a value not of that type.
- **The environment**, the host's `env`, is whatever the host gives one evaluation that does not belong in the expression, as DOMQL gives the window and the document a query runs against. Lexica passes it to every implementation and never reads it.
- **`beforeInvoke(request)`** is called before a member's implementation is invoked, with the request: the member's declaration, its receiver and arguments, and where it stands. It reports every invocation an evaluation attempts, whether it then succeeds, fails or is pending, so an observation covers a read whose implementation throws. For a member that reads maintained values it answers their samples, or that one is pending, and a member whose sample is pending is not invoked and reads as null.
- **`afterInvoke(request, value)`** is called only after an implementation answered a value of its result type.
- **`afterEvaluation(outcome)`** is called once, in a `finally`, with the evaluation completed, pending where a sample it read was pending, or failed. The evaluation runs to one of the three synchronously, so none is cancelled while it runs.
- **What reaches the hooks.** Only the invocations an evaluation reaches call `beforeInvoke`, so short-circuited operands and unselected branches record nothing, and a function the expression passes to a member keeps the member's invocation as its lifetime, closed before `afterEvaluation`.
- **Each evaluation its own.** An evaluation's state is its own unless its host shares it, as a watch shares its observations across evaluations, so an evaluation an implementation starts is isolated from the one that called it.
- **A hook that throws.** A throwing `beforeInvoke` or `afterInvoke` fails the evaluation at that member. A throwing `afterEvaluation` after a failure leaves the original failure thrown, the cleanup failure recorded on it, and after a success fails the evaluation itself.
- **Without hooks.** A host with nothing to observe gives the environment alone, and an evaluation without a `beforeInvoke` reads fresh members alone, refusing an expression that reads a maintained one.
- **What stays with the host.** Waiting for samples, cancellation between evaluations, watches and their scheduling, snapshots and live state, and subscriptions, actions and behaviors stay the host's: DOMQL carries them out as the observing host over Lexica's evaluation.

## Tooling

Preparation is authoritative: it validates every request against the vocabulary available before the request runs, whether text or a definition produced it. Three properties keep validation open to editor tooling, such as analyzers and completion, which can follow without changing the language:

- **Locations.** Text positions and definition-node locations are kept, so a diagnostic names the member, argument or object expression that failed; the mapping from text to definition can be kept apart from the definition.
- **Declarative metadata.** A module's declarations are data, so a tool understands them without running a capability's implementation.
- **Independent validation.** Structural and vocabulary validation run without a browser, given the metadata and the bindings' types.

A tool can check a query text known when the code is written against the metadata available to its project; text built at run time, modules registered at run time and checks that depend on bound values remain preparation's.

### Formatting

`lexica.format(source)` takes a text or a definition, and both give the same canonical text, which the definition writer writes; DOMQL's `domql.format` also takes a query object, which it formats from its definition.

- **What it keeps.** The definition's meaning, and the order of its locals and fields as declared; comments and the original layout are discarded, as a definition holds neither.
- **What it needs.** Neither bindings nor a registered vocabulary: it parses and checks structure as `lexica.parse` does, and resolves nothing.
- **The layout.** Four spaces of indentation for each level of an object expression; an object expression of one field and no locals on one line where its value is, `{ size = context.size }`, and any other with one line for each entry; a conditional with an `elseif`, or whose branches give their results with `return`, on one line for each clause and one for its `end`, each branch's locals and result a level within it; a body's locals and result each on a line of their own, a `do` block's a level within its `do` and its `end`; a string's line feed, carriage return, tab and escape character as `\n`, `\r`, `\t` and `\e`, and every other control, format or separator character in it but the space as `\u{…}`; an interpolated string's text as a string's with each brace doubled, and each interpolation's expression on one line, grouped in parentheses where it begins with one; one space on each side of `and`, `or`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `??`, `+`, `-`, `*`, `/`, `%`, `as` and `to`, and none between a negation's `-` and what it negates; and no trailing comma.
- **It is stable.** Formatting text already formatted gives the same text.
