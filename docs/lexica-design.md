# Lexica Design v1.0.0-alpha

The [Lexica specification](lexica-specification.md) defines the language. This design sets out how its modules are declared and registered, and how tooling reads its text; the [DOMQL design](https://github.com/FormaUI/DOMQL/blob/main/docs/domql-design.md) sets out how DOMQL prepares, evaluates and watches the queries written in it.

## Modules

An extension is registered as a module, which declares under its name the state members, event sources, actions and behaviors it contributes and supplies the implementation that carries each out; requests resolve against those declarations. The declarations are data, each member's DOMQL name, signature, result type, argument types and kinds and the request kinds it supports, so they can be read without running the implementations. A module associates two things explicitly, and neither is derived from the other: an operation's DOMQL name, `style`, and the function that carries it out, whatever that function is called. A module registers under a name of its own, and registering a name twice is an error.

```js
const virtualizer = domql.createModule('virtualizer', declarations, functions);

domql.registerModule(virtualizer);
```

### Declarations

A module is created with its members and, once it can carry them out, the functions they name; declarations are validated when the module is created and checked against the registry when it is registered. The built-in vocabulary is the module `builtIn`, whose identity no other module takes and whose members stand without a namespace; any other module adds members to its own types and a single member named for itself to any other, and declares conversions to and from its own types alone.

- **A declaration** names the member's DOMQL name, and the key of its function in the module's functions, independent of its name; its kind, one of property, operation, source, action and behavior; for a member that is no property, its form, a call by default or, for an operation, a named indexer, whose one required value parameter is its key, which can be the default indexer of its receivers, one for any receiver, and, where it has parameters, its input, positional, its parameters in order, or options, one object whose fields supply its parameters however many it has, as the specification sets out; the types it applies to; its parameters; its result type; its observation coverage; and, for a member that answers a number or a structured value holding numbers, the `tolerance` within which a watch compares each of them, exactly where it declares none.
- **A parameter** is a value or an expression. An expression is evaluated against each item of the list it follows and declares the type it produces. A parameter declares whether it is required, its default where it is not, and whether a null argument propagates, making the call answer null, or is accepted.
- **A fixed parameter** names something the vocabulary resolves before any evaluation, and declares what it selects: an event type or a condition.
- **A condition** names a Boolean of the receivers it applies to, the key of the function that tests it and its own contract, how it changes, how it reads, its misses and its observations, as a member's is. A member whose fixed argument selects a condition, as `is` does, names no function and derives how it changes: the resolution keeps both, the member, which gives the request its form, its argument and its type, and the condition, whose function carries it out and whose contract a watch checks and the evaluation follows, so one condition's observability is no other's. A module names conditions on its own types freely and a single one for itself on any other, as it does members, and a condition's failures name it, the member that selected it and its module.
- **Observations.** A member that changes observably or partly observably names the observations that cover its changes. An observation is of a type, observes the receiver, the receiver's root, its roots, the window, the document or an argument of the member, and gives the arguments its type takes, as `{ type: 'resize', of: 'receiver' }` does: a literal, a list of values, or an argument of the member, `{ argument }`, which can carry a prefix, a string joined before the argument of a value parameter of type `string`, as `{ argument: 'name', prefix: 'aria-' }` gives the attribute the ARIA view's indexer reads, so the observation names that attribute and is shared with every other observation of it; a member that changes in any other way names none. The receiver's **root** and its **roots** are those [trees and slots](https://github.com/FormaUI/DOMQL/blob/main/docs/domql-design.md#trees-and-slots) defines: a member that depends on the structure around its receiver observes its root, as `all` and `closest` do, and one that depends on any tree its receiver is shown in observes its roots, as `rect` does for scrolling. An observation of the roots is one request at each, so it is an invalidation, and a maintained observation, which gives its member one sample, observes one target. A module declares a type of observation by a camelCase name, its contract, the arguments that belong to an observation's identity, whether equivalent requests share one, and the function that starts one, which takes the request, the function it calls when something may have changed and the environment, and answers an object whose `stop` ends the observation and, for a maintained type, whose `sample` answers its latest sample as `{ pending, value }`, pending until the first arrives; a member reads the value, and is not called while a sample it reads is pending, answering null. An observation of a type that is not shared is kept for each watch, `evaluateAsync` call and event listener alone, so the sample it delivered reaches that caller's later evaluations. The built-in vocabulary's types are `resize`, `mutation`, `attachment`, `intersection`, `media`, `pixelRatio`, `event` and `visibility`, each shared; `intersection` is maintained, and the others are invalidations. A `resize` observes an element's border box, its content box, or both as its `client` box, DOMQL's combined mode, which starts one native observer for each box under one observation and lets go of the first where the second fails to start. A type is either an invalidation observation, which says that a result may have changed and carries no value, or a maintained observation, which provides a sample a member reads and is pending until its first arrives; a member that reads maintained values names a maintained observation, and no other member does.
- **Functions.** A member takes its receiver, its arguments by name and the environment, and a member that reads maintained values also their values, in the order its declaration names the observations. A source takes its receiver, its arguments, the environment and the function it delivers each event to, and answers an object whose `stop` ends the listening. An action takes its receiver, its arguments, the environment and `{ signal }`, and answers its result or a promise of it. A behavior takes its receiver, its arguments, the environment and `{ reportError }`, starts before it returns, and answers an object whose `update(receiver, args)` applies new arguments and whose `dispose` ends it.
- **A conversion** names the type of data it converts from, the one it converts to and the key of its function, one for each source type and target across every module registered, and none from a type to itself, which a value already of it converts to by the language's rule. Its types are `number`, `string`, `boolean` and the structured types that hold data alone, lists of data among their fields: a node and an event source are left to members, which declare how they change, so a conversion adds no dependency on the document, and a list itself is no type a conversion converts between. A conversion takes the value, never null, and `{ reject }`, reads nothing else, and answers the converted value, which is checked against the type it converts to, or calls `reject(reason)` where the value has none, with a reason that is a diagnostic string. `reject` throws a signal private to DOMQL and to that attempt at the conversion, so it never returns and the conversion stops where it calls it, unlike a promise's `reject`. A rejection is the one failure a conversion expects: `to` fails the evaluation for it and `try … to "type"` answers null, carrying the conversion out by one path, and any other exception, and a value not of the type, is a fault, which fails the evaluation for either. `to` takes one declared conversion and never chains them.
- **Types and events** are contributed by modules as data: structured types with their fields and event types with the type of their event data; a test is a member that answers a Boolean, and a capability a condition `supports` asks.
- **Observation coverage** states how a member changes (constant, observable, partly observable with the changes it misses, unobserved, or derived from the items it selects and the expression it evaluates) and how it reads (fresh, maintained, captured or derived).

`query.resolve(options?)` resolves a request: it resolves every member against the registry, types the result and records what each member resolved to, without a browser and without evaluating anything. A watch over a member that is unobserved is refused, and one over a partly observable member is refused unless it accepts partial observation.

A module is given the capability it exposes, never an instance of it, since instances belong to the callers that apply them. A module exposes a capability through DOMQL without the capability depending on DOMQL: the capability keeps an API of its own, and its module lives beside it or in an integration package for it.

- **The registry holds definitions.** Each DOMQL instance has one registry, which holds the declarations of every module registered with it, shared by all its callers. The instances behaviors create, the event listeners subscribed to them and the state of whoever applied them are scoped to their callers, never to the registry.
- **Registering is not applying.** Registering a module makes its capability understood; applying one of its behaviors creates an instance for its caller and target. Disposing that instance leaves the module registered.
- **Registering comes first.** A module is registered before a request naming it is prepared, and a member no registered module declares is a validation error naming it.

## Tooling

Preparation is authoritative: it validates every request against the vocabulary available before the request runs, whether text or a definition produced it. Three properties keep validation open to editor tooling, such as analyzers and completion, which can follow without changing the language:

- **Locations.** Text positions and definition-node locations are kept, so a diagnostic names the member, argument or object expression that failed; the mapping from text to definition can be kept apart from the definition.
- **Declarative metadata.** A module's declarations are data, so a tool understands them without running a capability's implementation.
- **Independent validation.** Structural and vocabulary validation run without a browser, given the metadata and the bindings' types.

A tool can check a query text known when the code is written against the metadata available to its project; text built at run time, modules registered at run time and checks that depend on bound values remain preparation's.

### Formatting

`domql.format(source)` takes a text, a definition or a query object, and all three give the same canonical text, which the definition writer writes.

- **What it keeps.** The definition's meaning, and the order of its locals and fields as declared; comments and the original layout are discarded, as a definition holds neither.
- **What it needs.** Neither bindings nor a registered vocabulary: it parses and checks structure as `domql.query` does, and resolves nothing.
- **The layout.** Four spaces of indentation for each level of an object expression; an object expression of one field and no locals on one line where its value is, `{ size = context.size }`, and any other with one line for each entry; a conditional with an `elseif`, or whose branches give their results with `return`, on one line for each clause and one for its `end`, each branch's locals and result a level within it; a body's locals and result each on a line of their own, a `do` block's a level within its `do` and its `end`; a string's line feed, carriage return, tab and escape character as `\n`, `\r`, `\t` and `\e`, and every other control, format or separator character in it but the space as `\u{…}`; an interpolated string's text as a string's with each brace doubled, and each interpolation's expression on one line, grouped in parentheses where it begins with one; one space on each side of `and`, `or`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `??`, `+`, `-`, `*`, `/`, `%`, `as` and `to`, and none between a negation's `-` and what it negates; and no trailing comma.
- **It is stable.** Formatting text already formatted gives the same text.
